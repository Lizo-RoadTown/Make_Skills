### Fixed

- **Add explicit `httpx>=0.27` to `platform/requirements.txt`** — fixes startup crash introduced by PR #71. PR #71's `services/skill_making/ack_sender.py` imports `httpx` for the registration-ack POST, but `httpx` was not declared as a direct dependency (it was a transitive dep of langchain). When `services/api/main.py` imports `compile_worker` → `ack_sender` → `httpx`, the deployed container's startup failed with ImportError and Render's load balancer returned 502 on all routes. Verified the failure mode via `https://make-skills-api.onrender.com/healthz` and `/bridge/promotion-candidate` both returning 502 after the PR #71 redeploy. Adding the explicit dep guarantees the import works regardless of langchain's transitive dep tree.

### Added

- **Engine telemetry collector hook — PR-prep-1 per `tapestry_canonical_framing_applied_2026_06_13`** (`services/skill_making/telemetry_collector.py`, `core/skill_making/compiler.py`, `core/runtime/runtime.py`, `services/api/main.py`, `services/skill_making/tenant_mapping.py`). Wires the runtime so every compiled-skill invocation emits a `TelemetryEvent` through the `telemetry_sender` shipped in PR #75 (which existed but was never called). New in-process collector with bounded asyncio queue (`MAX_QUEUE_DEPTH=10_000`) + background flusher (`BATCH_SIZE=100`, `FLUSH_INTERVAL_SECONDS=10.0`) + bounded shutdown drain (`SHUTDOWN_GRACE_SECONDS=5.0`). `compile_skill_to_tool` extended with `source_tenant_id` + `model_name` kwargs that are baked into each skill's `_run` closure — telemetry MUST NOT block the agent's response, so failures are caught + logged + swallowed. `AgentRuntime._resolve_agent` does an async reverse-lookup via the new `tenant_mapping.lookup_source_tenant(engine_tenant_id) -> source_uuid | None` helper once per cache miss; result is passed by kwarg into `_build_agent_from_config` (sync) so no ambient-context reads happen at invocation time. FastAPI lifespan starts the collector after `init_pool` and stops it before `close_pool`. **Tenants without a `tenant_id_mapping` row silently skip telemetry** (`source_tenant_id=None`) — skills still work; only observability degrades. Token counts extracted from langchain's `result.usage_metadata` (standard across Anthropic/OpenAI/Gemini per langchain_core's `BaseChatModel`). Privacy-bounded by `TelemetryEvent`'s `extra='forbid'`: only structural metadata. 6 new unit tests at `services/skill_making/tests/test_telemetry_collector.py` (lifecycle idempotence, batch flush, batch-size trigger, send-failure isolation, queue overflow). All 33 tests in `services/skill_making/tests/` pass locally (was 27 before this PR).

- **Wire-contract invariant tests at `services/skill_making/tests/`** — 27 pytest unit tests pinning the canonical `models.py` schema + the Stripe-style HMAC format. Catches the failure mode of the three spec-drift lessons by making schema/format changes loud at the test layer instead of silent until integration smoke. Two test files: `test_hmac_verify.py` (10 tests: valid/invalid signatures, timestamp window, secret mismatch, missing env var, signed-payload format with timestamp prefix) and `test_models_schema_invariants.py` (17 tests: non-nullable `tenant_id`, top-level `candidate_kind` + 9-kind taxonomy, `is_global` separate from `tenant_id`, `capability_tags` + `triggers` at top level not in frontmatter, `source.body_md` field name, `callbacks.telemetry` field name, `extra='forbid'` enforcement at every level, AckSkill + BridgeError + CompileOutcome enum exhaustiveness). Pure unit tests — no DB, no network. Run via `pytest services/skill_making/tests/`. All 27 pass at the time of this PR.

- **`GET /access/webhook/skill-promotion/versions`** endpoint (`services/api/main.py`) — schema-version discovery per wire-contract schema-versioning section. Returns `{"supported_versions": ["1.0"], "canonical": "1.0"}`. Lets the-loom (and any future bridge consumer) negotiate forward compatibility. Was missing from the engine; Loom-agent's audit caught it.

- **`services/skill_making/telemetry_sender.py`** — the third bridge message type per wire-contract section 3. `TelemetryEvent` + `TelemetryBatch` pydantic models + `send_telemetry_batch()` HMAC-signs (`X-MakeSkills-Signature` Stripe-style) and POSTs to `LOOM_TELEMETRY_CALLBACK_URL` (defaults to `loom-telemetry-ingestion.onrender.com/skill-used`). Same retry policy as `ack_sender` (3 attempts with exp backoff, no retry on 4xx). Privacy-bounded: structural metadata only — `skill_id`, `tenant_id` (source-side UUID, opaque), `outcome`, latency, token counts. NO user-message content, NO PII (enforced by pydantic `extra='forbid'`). Wiring from runtime invocation to this sender lives elsewhere and is a future PR; this module makes the send path callable from manual smoke or runtime collector when ready.

- **409 response body now carries `existing_skill_id`** per wire-contract section 1 — closes the audit gap Loom-agent caught. `services/skill_making/compile_worker.py` now calls `idempotency.update_response()` after compile succeeds, replacing the stored `{promotion_id, status: "queued"}` body with `{promotion_id, status: "compiled", existing_skill_id: "<uuid>"}`. The receiver's 409-on-duplicate path then replays the updated body, surfacing the skill_id the-loom needs for its dedup reconciliation path. New helper `idempotency.update_response()` performs an unscoped UPDATE on `bridge_idempotency` (no RLS — bridge infra). Pre-compile replays still 409 with `{status: "queued"}`; post-compile replays 409 with `existing_skill_id`. Both states are correct per spec semantic ("already accepted; here's the result").

- **`render.yaml` declares `LOOM_SKILL_BRIDGE_SECRET` + `LOOM_REGISTRATION_ACK_URL` env vars** (`sync: false`). The bridge receiver (PR #70) + ack sender (PR #71) read these via `os.environ` at runtime; the values live in the Render dashboard, the declarations live in the Blueprint. Without the Blueprint declaration, future Blueprint syncs from a clean state would not provision the env-var slots — the dashboard values would have to be re-added manually. Adding them here makes infra reproducible. No runtime behavior change; the receiver + ack sender already read from `os.environ`.

- **Phase 4 bridge receiver — back half (compile + ack)** (`core/skill_making/compiler.py`, `services/skill_making/{ack_sender,compile_worker,models}.py`, `services/skill_making/bridge_receiver.py`, `services/api/main.py`). Closes the bridge loop: queued candidates from PR A's front half now compile into `student_skills` rows and ack back to the-loom over the registration-ack callback. Key additions: (1) `core/skill_making/compiler.py` extends with `compile_from_bridge_candidate(pool, promotion_id, engine_tenant_id) -> CompiledSkillResult` — model-agnostic, no LLM at promote time; loads the `promoted_skills` row (RLS-scoped via `set_config('app.tenant_id', engine_tenant_id, true)`), resolves name collisions against the tenant's existing `student_skills` (appends `-promoted-N` up to 100 attempts before rejecting), INSERTs the skill with `agent_id=NULL` + `version=1`, UPDATEs `promoted_skills` to `status='compiled'` + sets `skill_id`. The existing runtime-side `compile_skill_to_tool` is unchanged — tool compilation against a specific model happens later at agent build time. (2) `services/skill_making/ack_sender.py` — POSTs a `RegistrationAck` to `LOOM_REGISTRATION_ACK_URL` (defaults to `https://loom-architecture-registry.onrender.com/skill-registered`), HMAC-signed with header `X-MakeSkills-Signature` in the same Stripe-style `t=<ts>,v1=<hex>` format the inbound uses. Retries 3x with exponential backoff (1s, 2s, 4s) on 5xx/network; never retries on 4xx (contract bug, not transient); raises `AckSendError` on final failure. (3) `services/skill_making/compile_worker.py` — orchestrates the compile → ack chain. Receives `engine_tenant_id` as an **explicit argument** (NOT via ContextVar) per the recorder convention at `core/auth/tenant_context.py:18` — background tasks lose request scope. Builds the ack body using `source_tenant_id` (the loom-side UUID, NOT `engine_tenant_id`) for `AckSkill.tenant_id` because the-loom scopes by source UUIDs (`loom_agent_bridge_complete_status_and_secret_2026_06_12_evening`). Compile failures get acked as `outcome=rejected` with diagnostics; ack-send failures log loudly but don't crash — engine state stays at `compiled` so a future repair script could re-ack; the-loom dedups by `promotion_id` so re-acks are safe. (4) `services/skill_making/bridge_receiver.py` — `ReceiverResult` gains a `compile_request: tuple[UUID, str] | None` field. Set to `(promotion_id, engine_tenant_id)` ONLY for `kind=skill` candidates; non-skill kinds (ack-deferred) leave it `None`. Receiver stays transport-agnostic — the route does the actual `BackgroundTasks.add_task` scheduling. (5) `services/api/main.py` — `bridge_promotion_candidate` route injects `BackgroundTasks`; after the receiver returns 202, schedules `compile_and_ack(pool, promotion_id, engine_tenant_id)` to run after the response is sent. Loom side gets a fast 202; the compile + ack chain runs out-of-band. (6) `services/skill_making/models.py` — adds `CompileOutcome` enum, `AckSkill`, `AckDiagnostics`, `AckLoomMetadata`, `RegistrationAck` per wire-contract section 2. (7) `scripts/verify_bridge_receiver.py` — new scenario 7 exercises the full compile path: receiver creates `compile_request`, script calls `compile_and_ack` directly, asserts `promoted_skills.status='compiled'` + `skill_id` set + `student_skills` row written with the expected name. Cleanup teardown updated to also DELETE the `student_skills` rows the compile created. Both modes verified at every edit point per discipline hooks.

- **Phase 4 bridge receiver — front half (guard + intake, no LLM)** (`services/skill_making/{bridge_receiver,models,tenant_mapping,hmac_verify,idempotency}.py`, `services/api/main.py` route, `core/db/migrations.py` migration). The bridge receiver stub at `services/skill_making/bridge_receiver.py` is replaced with a deterministic guard + intake layer that consumes promotion candidates from the-loom over the wire contract at `docs/proposals/2026-05-25-skill-making-bridge.md` (shaped per the revised Phase 4 sketch in PR #69). New POST `/bridge/promotion-candidate` route on the FastAPI app — HMAC-SHA256 authenticated via `X-Loom-Signature` header in **Stripe-style `t=<unix_seconds>,v1=<sha256_hex>` format** (HMAC over `"<ts>.<raw_body>"`, ±5 minute replay window) against shared secret `LOOM_SKILL_BRIDGE_SECRET`, matching loom side's PR #21 wire format per `loom_agent_bridge_complete_status_and_secret_2026_06_12_evening`; NOT consumer JWT (the bridge is a service-to-service contract). Per-candidate flow: HMAC verify → schema validate (pydantic, top-level `candidate_kind` for the 9-kind taxonomy + non-nullable `tenant_id` UUID + separate `is_global` flag) → idempotency check (Postgres-backed by `promotion_id`, replay safe) → tenant resolution via `tenant_id_mapping` table (Option B from `decision_tenant_id_mapping_option_b_2026_06_12` — explicit cross-system UUID reconciliation, no silent fall-through) → kind dispatch (`kind=skill` persists as `status='queued'` for PR B's compiler; other 8 kinds persist as `status='kind_not_yet_handled'` with 202 + `outcome='ack_deferred'` per Loom-agent's ack-defer ratification in `loom_agent_to_ms_agent_ack_defer_ratified_2026_06_12_evening`) → response recorded for idempotent retries. New tables: `tenant_id_mapping` (unscoped, seeded with the-loom's self-host `1d8ec1b3-...` → engine's `00000000-...` mapping), `bridge_idempotency` (unscoped, `promotion_id`-keyed response replay), `promoted_skills` (RLS-scoped by `engine_tenant_id`). Verification script `scripts/verify_bridge_receiver.py` exercises 6 scenarios end-to-end (HMAC mismatch / schema fail / happy skill / non-skill ack-defer / replay-409 / unknown-tenant-400) against a live Postgres. Companion `get_pool()` helper added to `core/db/db.py` for pre-tenant-context lookups (mapping resolution, idempotency check) with docstring guardrail steering tenant-scoped reads back to `tenant_conn`. Compiler dispatch + ack sender (the "back half") ship in PR B per the sketch's two-PR split.

- **Initial public release as a module of the-loom platform.** Make_Skills ships its three-layer engine — `core/` (reusable engine: runtime, skill compilation, model registry, subagent orchestration, auth, db, providers, tools), `adapters/` (project-type adapter stubs: classroom, development, research-project), `services/` (FastAPI app + admin + skill-making bridge stub) — plus a 16-skill methodology library (`skills/` + `skills_private/`) and 4 specialized subagent definitions. Two-mode supported from day one (`PLATFORM_MODE=self_host` default; `PLATFORM_MODE=hosted` for multi-tenant deployments behind a consumer app's JWT). Apache 2.0 licensed.

  Memory storage is delegated to the-loom (see [CLAUDE.md](CLAUDE.md) CORE DIRECTIVE 1) — Make_Skills no longer self-hosts a memory subsystem. The boundary rule: *Make_Skills improves local agency and produces candidates. The-loom observes across projects, governs promotion, and stores durable structure.*
